# beta.67 调查文档核验与待审批方案

日期：2026-09-04。依据：用户提供的 beta.67 调查文档、修改前 beta 工作树、beta.67 发布实现。本文是调查与方案，不表示长列表架构改造已经获批或完成。

## 核验结论

**架构事实大部分属实；“哪个因素占主要耗时”“能消灭多少卡顿”仍是推测，不能从静态代码直接定量确认。** 文档末尾多处重复条目应合并，不代表多个独立问题。

| 文档主张 | 核验 |
| --- | --- |
| 待复习列表内挂载真实 iframe，没有虚拟列表 | 属实。DueReviewList 对 visibleRecords.map，每张卡片的原题/答案仍在正常文档流中 |
| 点击单题会重新执行整段列表组件 | 属实。预览、缩放、历史等状态在列表级，单卡未 memo；但重新协调不等于所有 DOM 都实际重绘 |
| 重复 filter/map 与未隔离更新 | 属实。需用性能采样区分它与绘制、图片解码、桥接各自成本 |
| 原题反复 scrollHeight 改高导致持续整列表重排 | **部分属实**。beta.67 有多次读取，但首次高度缓存为300—520px；后续调用复用缓存。不能描述成每次缩放都持续撑高列表；待复习答案本身已是固定 viewport |
| HTML 与父 iframe 重复绑定手势 | 属实。card-html内置脚本、详情wirePreviewFrame、复习答案wireReviewAnswerFrame各自持有缩放状态，基础手势函数虽共用，控制器仍重复 |
| will-change常驻/100% transform | 属实，属于潜在合成成本；实际是否增加特定设备GPU层须工具采样 |
| mistakeDetail同时生成原题和全部候选答案 | 属实。mistakeDetailById无include参数，展开原题也做答案工作 |
| 图片Base64内嵌srcDoc | 属实。增加字符串与传输成本；不能把每张资源假设为2MB，实际量取决于题目 |
| 整条链都是WKWebView | **不准确**。原生代码声明new UIWebView；不能仅凭命名断言具体MarginNote版本底层实现或内存合成行为 |
| “只展开一个也卡”能排除长列表影响 | 不能排除；文档对此反驳合理。但也不能仅凭相关性确定iframe就是唯一根因 |

关键源码：web/src/main.jsx中的DueReviewList；src/mistake-manager.ts中的mistakeDetailById；src/card-html.ts；原beta.67的wirePreviewFrame/applyReviewFrameScale/wireReviewAnswerFrame；rails-native/WebPanelController.js。

## 已直接处理，与第7项重合的边界

用户明确要求直接统一题目/答案预览，因此beta.68已实现：

```text
原题/答案内容 → renderCardHtml（保留）
                        ↓ 同一 mountCardPreview + wireFramePinchZoom
       ┌────────────────┴────────────────┐
       原生答案 UIWebView                 Web CardPreview
                                ┌─────────┴─────────┐
                                详情原题/答案        待复习原题/答案
```

- 不重写卡片解析器，不拆现有mistakeDetail契约。
- 删除父页面三套预览控制代码，复用HTML内已有控制器；没有给同一文档再安装第二套。
- 原题仍保留首次测量后固定高度的展示习惯，只移除后续重复定时测量；答案viewport仍固定。
- 导出是纸张/静态排版，不强行套上交互预览窗口；继续复用卡片内容生成。
- **未实施：预览移出列表、虚拟列表、ReviewCard拆分、按需bridge或图片文件资源化。**

## 建议审批的下一阶段

### 第一阶段：不改变使用位置，先隔离长列表更新

1. 提取ReviewCard，单题展开/历史状态归属单卡；memo并稳定回调、数据引用。
2. 统计与筛选集中memo，缩放过程中不更新整个列表。
3. 将复习原题也改为由容器确定的固定viewport，不再读取内容高度决定卡片高度；内部原生单指滚动，保留现有“题目下展开”的位置。
4. 保留当前数据接口、全部展开/收起、时间轴、队列筛选、评级和定位功能。

这一阶段的可见变化只有原题预览采用固定视窗。**建议先批准此阶段。**

### 第二阶段：千题规模的有界DOM

1. 为待复习列表加入可变高度虚拟化，只挂载视窗和缓冲区的卡片；展开、历史、定位记录状态独立保存。
2. 正确维护滚动锚点；回到旧题不丢展开/答案候选；跳到指定复习记录先按索引定位再测量。
3. 不把content-visibility作为唯一方案，需兼容宿主WebView能力。
4. 独立预览浮层/右侧面板可进一步隔离iframe，但会改变布局，**未经另行批准不采用**。

### 第三阶段：减少数据与图片工作

1. mistakeDetail增加可选includeQuestion/includeAnswers，旧调用默认保持完整返回；原题和答案分别按需请求、缓存与失效。
2. 首屏继续先传25条；审计原生全库汇总/排序与历史数据体积，避免“分页传输”掩盖之前的全量计算。
3. 图片临时文件URL替代Base64放到最后，先验证本地文件访问权限、清理周期、引用生命周期及导出兼容性，不能直接批量替换。

## 验收方案

- 数据集：50/500/1000题；纯文字、图片、手写混合；收起、单题展开、多题展开三种状态。
- 记录：首次外壳时间、首批数据时间、全部传输时间、展开延迟、滚动帧耗时、DOM/iframe数量、桥响应字节数。
- React验证：展开一题只更新相关单卡；缩放不触发整列表render；虚拟化后DOM数量受视口限制。
- iPad真机：单指滚动/双指缩放、切候选、横竖屏、跳转原题、历史时间轴、复测后队列变化。
- 不以桌面Chrome时间推算iPad千题耗时，不承诺未经实测的提升百分比。

## 原生闪退另案

该调查文档没有系统崩溃堆栈，无法用它确认悬浮球闪退根因。beta.68已移除菜单/开关经过宿主自定义boolean方法的链路，显式传入所属addon，并修正带冒号点击回调及菜单外关闭的控件入口；这些是代码修复，不等于取得了真机崩溃根因证明。仍应取得beta.67或beta.68的.ips报告进行定位。
